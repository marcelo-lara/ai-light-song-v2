# EPIC 5 - Story 5.6

## LLM-Friendly Event Timeline Export

## Goal

Export a compact, lighting-relevant event timeline that summarizes machine and human-reviewed musical events without embedding raw feature arrays.

## Inputs

- merged or machine-only event outputs from Story 5.5
- canonical event vocabulary and schema from Story 5.1
- section references and supporting evidence summaries from upstream artifacts

## Dependencies

- a compact export shape suitable for downstream prompting
- stable merge rules when human overrides exist
- optional high-level lighting hints that remain editable and non-binding

## Processing Steps

1. Merge machine output with human overrides when they exist, using documented precedence rules.
2. Export a condensed event timeline in JSON and markdown with time range, event type, confidence, intensity, short notes, evidence summary, and explicit `created_by` provenance of the form `analyzer_{module/algorithm/model}`.
3. Attach optional high-level lighting hints for event types such as `drop_explode`, `anthem_call`, `groove_loop`, or `atmospheric_plateau`.
4. Keep raw arrays and detailed supporting evidence in separate files and reference them instead of embedding them.
5. Preserve whether each event is machine-only, human-confirmed, or human-edited.
6. **Composite gestures (v2.1, item 4.1).** After the merge, fold a `build → drop → post_drop` run (within an 8 s window) into **one** row with `composite: true`, an overall `start_time`/`end_time`/`confidence`/`intensity`, `member_event_ids[]`, and an ordered `phases[]` — each phase `{phase, start_time, end_time, intensity}` with `phase ∈ {approach, build, tension, impact, release, recovery}`, covering the composite's span contiguously. The phase members are **not** emitted as independent rows. A `build` with no resolving `drop` folds into a composite with **no `impact`/`release` phase** (the withheld-release / `fake_drop` case) so a consumer never handles phases in two shapes. `song_event_timeline.json` `schema_version` → `"1.1"`, engine → `llm-friendly-event-timeline-v2`.
7. `beatdrop_visual_plan.json` keeps reading the flattened view for v2.1 (it is built from sections/energy/fft, not this timeline) — composite consumption there is v2.2.
8. **Lean timeline (v2.1, item 4.2).** `layer_add` / `layer_remove` are **not** timeline events (they were the sub-second dense-blip anti-pattern). Arrangement change is summarised per section in `texture_summary[]` — `{section_id, start_time, stem_activity{bass,drums,harmonic,vocals}, stems_entering[], stems_leaving[]}` — carried on `events.machine.json` metadata and echoed on the exported timeline.
9. **Absolute `intensity` (v2.1, item 4.2, B4).** `intensity` in the export is an **absolute cross-song magnitude**, not a per-song normalisation. Each event type has a fixed `[floor, ceiling]` band; the raw signal only positions the event inside its band. A quiet track's loudest moment therefore stays below a loud track's, and the field spreads across its range instead of piling at `1.0`.
10. `summary` for each row is taken from the evidence summary (which describes the musical moment) rather than the rule note (which restates the rule that fired).

## Output Artifacts

- `data/analysis/<Song - Artist>/song_event_timeline.json`
- `data/analysis/<Song - Artist>/artifacts/validation/song_event_timeline.md`

## Acceptance Criteria

- The exported timeline is compact enough for LLM or planning use.
- Each event includes enough context for show-planning decisions without requiring raw-array inspection.
- Lighting hints remain high-level and editable rather than fixture-specific mandates.
- The export preserves review provenance for each event.
- The JSON export remains part of the stable UI output contract, and the markdown companion does not add a second markdown file under `data/analysis/<Song - Artist>/`.

## Validation

- Confirm the JSON and markdown outputs contain the same event set and timing.
- Confirm timeline entries reference supporting evidence rather than duplicating large feature payloads.
- Confirm every inferred timeline entry carries an explicit `created_by` value that identifies the inferring analyzer module, algorithm, or model.
- Confirm human-authored show notes can override generic lighting hints when present.

## Failure Cases

- The export embeds raw feature arrays and becomes too large for downstream prompting.
- Lighting hints become fixture-specific instructions.
- Provenance is lost during machine and human merge.

## Out of Scope

- Fixture-aware orchestration
- ML training and evaluation
- Real-time control transport
